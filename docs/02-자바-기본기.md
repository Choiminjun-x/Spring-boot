# 2회차 — 자바 기본기

## 메모리

### 스택(stack)

- 메서드 호출마다 한 칸씩 쌓이는 공간. 지역변수가 여기에 존재
- 스레드마다 하나씩 존재

### 힙(heap)

- new로 생성한 객체 본체가 있는 공간.
- 프로세스 전체가 공유

### 대입과 인자 전달

- 넘어가는 건 주소값의 복사본이다. 그래서 객체는 공유되지만 변수는 공유되지 않는다.

```java
class Box {
    int value;
}

static void a(Box b) {
    b.value = 99;            // b가 가리키는 객체를 건드림
}

static void c(Box b) {
    b = new Box();           // b라는 변수를 건드림
    b.value = 99;
}
```

```java
Box x = new Box();
x.value = 1;

a(x);
System.out.println(x.value);   // 99

c(x);
System.out.println(x.value);   // 1
```

### 필드는 어디 사는가?

- 타입이 아니라 소속이 결정한다
- 메서드에 속한 것(지역변수, 매개변수) -> 스택
- 객체에 속한 것(필드) -> 힙, 그 객체 안에

```java
class User {
    String name;     // 힙 (User 객체 안)
    int age;         // 힙 (User 객체 안)
}

void doSomething() {
    User u = new User();   // u는 스택, new User()로 만들어진 객체는 힙
    int count = 0;         // 스택
}
```

`int` 가 두 번 나온다. `int age` 는 필드라 힙, `int count` 는 지역변수라 스택.

### null

- NPE는 null을 꺼낼 때가 아니라 null을 통해 뭔가를 시킬 때 발생

```java
class User {
    String name;
    int age;
}

User u = new User();

System.out.println(u.age);           // 0
System.out.println(u.name);          // null
System.out.println(u.name + "!");    // null!
System.out.println(u.name.length()); // NullPointerException
```

### equals, ==

- 메서드를 부르는 주체가 누구인지가 중요
- `"abc".equals(s)` -> 주체는 `"abc"`
- 비교할 때는 확실한 쪽은 앞에 둔다 - `상수.equals(변수)`
- `==` -> 변수에 담긴 값을 비교, 참조형이면 주소값 비교 = "같은 객체인지"
- `equals` -> 객체가 스스로 정의한 내용 비교 = "같은 값이냐"

### static 변수

- 정적 변수는 힙에 존재, 객체 밖에 하나
- 클래스 로딩 시점에 자리가 잡힘 -> 애플리케이션 끝날 때까지 남음
- 객체를 넘나드는 정보를 담는 자리
- 모든 스레드가 공유 -> 힙은 프로세스 전체가 쓰기 때문
- 변하는 값은 정적 변수에 두지 않는다

### GC

- 힙에서 "더 이상 도달할 수 없는 객체"를 찾아 회수하는 JVM의 기능
- "안 쓰는 객체"가 아니라 도달 가능성(reachability)을 확인한다
- 메서드가 끝나면 스택 칸은 통째로 사라짐, 힙에 만들어진 객체는 안 사라짐 -> 이걸 그대로 두면 힙이 계속 차오른다. 그래서 JVM에 GC(Garbage Collector)가 존재
- GC가 언제 돌지는 JVM이 알아서 결정 -> 개발자는 GC 시점을 제어할 수 없다
- GC가 돌 때는 애플리케이션이 잠깐 멈춤 -> 그동안 요청 처리 지연, 서버 장애 원인으로 실제 등장하는 항목
- GC가 있어도 메모리 누수는 발생한다 -> GC의 기준이 "도달 못 하는 것"이라서, 안 쓰는데 어딘가에서 계속 참조를 붙들고 있으면 살아 있다고 판단

## 상속 vs 인터페이스

### 인터페이스

- "무엇을 할 수 있는가"만 정의, 구현은 분리
- 쓰는 쪽이 "어떻게"를 알면 구현을 바꿀 때마다 쓰는 쪽이 바뀐다

### DI(의존성 주입)

- 자기가 쓸 것을 직접 만들지 않고 밖에서 받는 것
- 구현을 바꿔도 쓰는 쪽 코드는 안 바뀐다. 테스트할 때 가짜 객체를 넣기도 수월

### IoC(제어의 역전)

- "무엇을 쓸지 정하는 권한"이 자신에게서 밖으로 넘어간 것

```java
// 1단계
class OrderService {
    EmailSender sender = new EmailSender();   // 바꾸려면 이 파일을 고쳐야 함
}

// 2단계 — 인터페이스 도입
class OrderService {
    NotificationSender sender = new EmailSender();   // 타입만 바뀜, new는 그대로
}

// 3단계 — DI
class OrderService {
    private final NotificationSender sender;

    OrderService(NotificationSender sender) {   // 밖에서 받는다
        this.sender = sender;
    }
}
```

### 상속

- 부모의 필드와 메서드를 자식이 물려받는 것. 코드 재사용 수단이지만, 자식이 부모의 구현에 묶이는 강한 결합이다
- 자바는 클래스를 하나만 상속할 수 있다
- `extends` 는 하나, `implements` 는 여러 개
- 상속보다 인터페이스(합성)를 먼저 고려한다 -> 실무 원칙

### 상속은 "~이다", 인터페이스는 "~할 수 있다"

- Dog is an Animal
- EmailSender can send
- EmailSender is a NotificationSender -> 어색함

### 객체지향 4대 특성

- 캡슐화 - 내부를 감추고 필요한 것만 공개
- 상속 - 부모의 필드와 메서드를 자식이 물려받는 것
- 다형성 - 같은 코드가 실제 객체에 따라 다르게 동작
- 추상화 - 구체적인 것 말고 본질만 남김

### 상속보다 합성(Composition over Inheritance)

- "~이다"면 상속, "~을 갖고 있다"면 합성
- 코드를 공유하고 싶다는 이유만으로 상속하지 않는다

```java
// A — 상속
abstract class AbstractSender implements NotificationSender {
    void log(String message) { }
}
class EmailSender extends AbstractSender { }

// B — 합성
class EmailSender implements NotificationSender {
    private final Logger logger;      // 물려받는 게 아니라 갖고 있는 것
}
```

## 제네릭

- 타입을 밖에서 지정해서, 실행 시점에 터질 일을 컴파일 시점으로 옮기는 장치
- `<>` 안에 들어가는 건 클래스만 가능, `List<int>` X -> `List<Integer>`

## 컬렉션

- List - 순서가 있고 중복을 허용. ArrayList
- Set - 순서가 없고 중복을 허용하지 않음. HashSet
- Map - 키 -> 값 짝. 키는 중복 불가. HashMap
  - equals를 구현하면 hashCode도 반드시 같이 구현해야 한다

## 예외(throw)

- 메서드가 정상적으로 값을 돌려주지 못하는 상황이 있다. 파일이 없거나 DB 연결이 끊겼거나, 인자가 말이 안되거나. 이 때 자바는 예외 객체를 만들어 던진다
- checked vs unchecked
  - checked 예외 - 컴파일러가 처리를 강제한다. IOException, SQLException
  - unchecked 예외 - 강제하지 않는다. RuntimeException, NullPointerException, ClassCastException이 여기에 속함
  - 스프링은 데이터 접근 예외를 전부 unchecked로 바꿔서 던진다
  - 현대 자바 실무의 기본 방침은 - 직접 만드는 예외는 RuntimeException을 상속한다
- finally
  - 예외가 나든 안 나든 반드시 실행 - 자원 정리에 사용됨
